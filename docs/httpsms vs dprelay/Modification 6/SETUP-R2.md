## 1. What is actually free (and the one catch)

| Resource | Free allowance / month | Our expected use |
|---|---|---|
| Storage | **10 GB** (permanent tier, not a trial) | DB backups < 1 GB for a long time; attachments = the real consumer |
| Class A ops (writes/lists) | **1 million** | Litestream segment writes worst-case ~170k/mo if the DB changed nonstop |
| Class B ops (reads) | **10 million** | Presigned attachment GETs, Litestream restores — negligible |
| **Egress (downloads to internet)** | **$0 — unlimited** | The reason R2 beats S3/B2 for us |

> ⚠️ **FLAG:** Activating R2 **requires a payment card on file even on the Free plan**, and the free tier is *not hard-capped* — usage beyond the allowances bills that card. Staying at $0 is a monitoring discipline, not a platform guarantee: set the billing alert in §6 before anything else.

## 2. Account + R2 activation

1. Sign up / log in at `https://dash.cloudflare.com` (a free Cloudflare plan is enough; you do not need a domain on Cloudflare to use R2).
2. Left sidebar → **R2 Object Storage**.
3. First time: click **Purchase R2** (or "Get started") → choose the **Free** plan → add the payment card when prompted. You will not be charged while within the §1 allowances.
4. Note your **Account ID** — shown on the R2 overview page (right-hand column) and later on the API-token page. Every S3 endpoint URL embeds it.

## 3. Create the two buckets

R2 overview → **Create bucket**:

| Bucket name (suggestion) | Purpose | Settings |
|---|---|---|
| `dprelay-litestream` | Continuous SQLite backup stream | Location: **Automatic** (or APAC if you want it near the Render Singapore / Oracle region). Default: **private**, no public access, ever |
| `dprelay-attachments` | MMS attachment blobs (M5) | Same location choice. Private — access only via **presigned URLs** generated by the v5 server |

Objectives for naming: lowercase, hyphens, globally unique within *your* account.

## 4. Create the S3 API token (what Litestream and the server use)

1. R2 overview → **Manage R2 API Tokens** (usually top-right) → **Create API Token**.
2. Permissions: **Object Read & Write**.
3. Scope: **Apply to specific buckets only** → select both buckets from §3 (least privilege; add a separate token later if you ever want per-service credentials).
4. TTL: leave unlimited for now; rotate deliberately via the dashboard.
5. Create, then **copy immediately**:
   - **Access Key ID**
   - **Secret Access Key** *(shown exactly once — if lost, regenerate)*
   - **S3 endpoint**: `https://<ACCOUNT_ID>.r2.cloudflarestorage.com`
6. Store these in the server's env (§5). Never in code, never in git.

## 5. Wire-up configuration

### 5.1 Environment variables (server + Render/Oracle service)

Per repo rules these belong in `docs/Plan/11-ENV-VARS.md`, `README.md`, and `.env.example` when M1 implements them:

```
R2_ACCOUNT_ID=            # from §2.4
R2_ACCESS_KEY_ID=         # from §4.5
R2_SECRET_ACCESS_KEY=     # from §4.5
R2_ENDPOINT=https://${R2_ACCOUNT_ID}.r2.cloudflarestorage.com
R2_BUCKET_LITESTREAM=dprelay-litestream
R2_BUCKET_ATTACHMENTS=dprelay-attachments
```

### 5.2 Litestream config (M1, both host options A and B)

```yaml
dbs:
  - path: /data/dprelay.db
    replicas:
      - type: s3
        bucket: ${R2_BUCKET_LITESTREAM}
        endpoint: ${R2_ENDPOINT}
        region: auto               # R2 ignores region but the SDK wants a value
        access-key-id: ${R2_ACCESS_KEY_ID}
        secret-access-key: ${R2_SECRET_ACCESS_KEY}
        retention: 168h            # 7 days of point-in-time recovery — far under 10 GB
        sync-interval: 15s         # worst-case ~1 point of data loss window
```

Boot pattern differs by host:

- **Oracle (A, persistent disk):** start app, Litestream streams out; `restore -if-db-not-exists` only on fresh volumes.
- **Render (B, ephemeral disk — R2 constraint):** container entrypoint must run `litestream restore -if-db-not-exists /data/dprelay.db` **before** the Fastify process starts, every boot. Keep the DB compact so restore stays in single-digit seconds.

### 5.3 Attachments (M5)

Server generates **presigned PUT/GET URLs** against `R2_BUCKET_ATTACHMENTS` using any S3-compatible SDK (`@aws-sdk/client-s3` + `@aws-sdk/s3-request-presigner`) pointed at `R2_ENDPOINT`. Enforce per-attachment size caps (e.g., 5 MB) and a cleanup policy (e.g., 30-day TTL) in the job runner so the 10 GB allowance is never a concern.

## 6. Guardrails (do these before M1 go-live)

1. **Billing alert:** Dashboard → Billing → Alerts → create an alert at **$1.00/month**. If it ever fires, something is leaking writes or storage — investigate before the invoice exists.
2. **Token hygiene:** one token, two buckets, Object Read & Write only. No account-level tokens. Rotate by creating a new token, deploying, then deleting the old one.
3. **Never make either bucket public.** Attachments are private-by-presign; backups are private-forever.
4. **Quarterly check:** R2 overview shows usage meters against the free allowances — glance at storage + Class A ops each quarter.

## 7. Cost projection at our scale

| Consumer | Monthly |
|---|---|
| Litestream writes (~170k worst-case Class A) | $0 (1M free) |
| Litestream storage (7-day retention, DB « 1 GB) | $0 (10 GB free) |
| Attachments @ 5 MB cap, moderate MMS volume | $0 within ~2,000 stored attachments |
| Egress (restores, attachment downloads) | **$0 always** |
| **Total** | **$0** — with the §6 alert as the tripwire |
